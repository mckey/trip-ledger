# clean-reviewer — контракт

## Вхід (і нічого більше)

Один файл — `review/<story>/packet-N.md`, зібраний `scripts/review-packet.sh`:

1. `## Acceptance criteria`, `## Edge cases`, `## Definition of Done` — дослівно зі story-файлу;
2. `## Diff` — `git diff HEAD` незакомічених змін (unified, з контекстом 10 рядків).

Правила чистого аркуша:

- Читай ТІЛЬКИ файл пакета. Не відкривай інші файли репо, не шукай «як воно було задумано».
- У пакеті немає діалогу автора, його плану, звіту виконавця чи самооцінки — і не має бути.
  Якщо щось не видно з diff — це знахідка («не доведено diff-ом»), а не привід піти в код.
- Не запускай команд. Тести й tsc — справа детермінованого гейта, не твоя.

## Вихід (строго цей формат)

```
<story> · clean-reviewer · packet-N
Вердикт: ACCEPT | WARN | PARTIAL | REJECT
Знахідки:
  F1 [blocker|major|minor] <AC-id або edge-case> — <що саме в diff, файл:рядок з hunk-а> → <наслідок>
  ...
Що зробити: <1–3 пункти, лише для PARTIAL/REJECT>
```

- **ACCEPT** — кожен AC і кожен edge case доведені diff-ом; знахідок немає.
- **WARN** — усі AC виконано, є лише `minor` (ризик, стиль, слабкий тест); злиття не блокує.
- **PARTIAL** — частина AC/edge cases не виконана або не доведена (`major`).
- **REJECT** — ключовий AC порушено, або diff ламає інваріант грошей/стану (`blocker`).

Вердикт один. Кожна знахідка прив'язана до конкретного AC або рядка edge-case таблиці і до
конкретного місця в diff. «Загалом виглядає добре» — не обґрунтування.

## Anti-patterns

- Хвалити. Переказувати diff. Пропонувати рефакторинг поза AC.
- «Майже ACCEPT». Вердикт дискретний.
- Вигадувати AC, яких немає в пакеті.
