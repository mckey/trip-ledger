# Skill: discovery — ideation-інтерв'ю під мою практику

Той самий каркас, що у `sdlc:interview` (14 фаз, read-only до ExitPlanMode, артефакт — один idea-brief), але промпт-секції, персони і шаблон переписані під те, як я реально відбираю фічі: робочий B2B travel-проект з живим легасі та сезонністю — і pet-інструменти, де користувач один.

## Відмінності від готового interview (навіщо форк)

1. **Сократ під мій домен** (Phase 2) — додані категорії «хто платить vs хто користується», «дедлайн сезону», «паритет з легасі».
2. **Конкуренти без вигадування ринку** (Phase 4) — для внутрішніх/pet фіч дефолт «сусідні інструменти, якими вже користуюсь», а не 5 конкурентів з пошуку.
3. **Підходи = мої типові альтернативи** (Phase 5) — Reuse / Integrate / Build-minimal.
4. **Support замість Executive** (Phase 6) — у travel перша лінія болю — техпідтримка; для pet «бізнес-погляд» — вода.
5. **Правило малої бази у RICE** (Phase 9) — Reach < 10/квартал → проходить тільки Effort S, інакше різати scope або в парк.
6. **Self-check під мій стек** (Phase 13) — регекс заборонених термінів розширено назвами мого стека.
7. **Шаблон з моїми плейсхолдерами** — «хто платить/хто користується», «дедлайн сезону», «сигнал у саппорт», «наступна фіча, яку розблокує», секція «Слід у словнику».

## Owner

Автор ідеї (зазвичай я). На робочих фічах — плюс той, хто відповідає за модуль-легасі-двійник.

## When to use

- «discovery для <slug>», «бриф для <фічі>», «/discovery <slug>», «нова фіча <slug>».
- Skip, якщо `docs/features/<slug>/idea-brief.md` вже існує зі `status: Confirmed` і свіжий (≤2 тижні) — оновлюй, не переписуй.
- Glossary-aware: на старті читає `CONTEXT.md` (корінь або `docs/features/<slug>/`), тримає словник у контексті сесії; нові доменні слова збирає у `pending_glossary_terms` і застосовує у Phase 12.

## Mode handling

Як у оригіналі: Phases 0–11 read-only (Read, WebSearch, Agent, AskUserQuestion), Phase 11.5 — ExitPlanMode, Phases 12–14 — записи. AskUserQuestion у Phases 1, 2, 9, 10, 11 — обов'язковий ввід даних, Auto Mode його не скасовує; фабрикація відповідей = недійсний бриф. Питання — українською, у стилі «контекст → чому важливо → яка думка потрібна».

## Protocol (14 фаз)

### 0. Pre-plan setup (read-only)
Read `./templates/idea-brief.md` + `CONTEXT.md`. Перевір, що Confirmed-бриф для slug не існує. Жодних записів.

### 1. Idea capture (AskUserQuestion)
«Опиши ідею в 1–3 реченнях своїми словами». Зберегти дослівно як §1.

### 2. Socratic deep dive (AskUserQuestion, батчами по 2–3)
3–5 питань з МОЇХ категорій:
- **Чіткість проблеми** — конкретний епізод, де боліло, з числами.
- **Хто платить vs хто користується** — у B2B travel це різні люди (агенція платить, агент клацає, турист відчуває); для pet чесно записати «я і я».
- **Дедлайн сезону** — travel живе сезонами: фіча, що не встигла до високого сезону або до найближчої поїздки, чекає рік. Яка дата робить фічу непотрібною до наступного вікна?
- **Паритет з легасі** — чи існує легасі-реалізація/сусідній модуль, з яким користувач звик порівнювати? Що з його поведінки зобов'язані повторити?
- **Критерій успіху** — одна метрика, яка зрушиться.

### 3. Glossary capture (deferred)
Нові доменні слова → `pending_glossary_terms` (термін + чернетка NOT-межі проти найближчого омоніма з CONTEXT.md). Застосування — у Phase 12.

### 4. Konkurenty / сусідні рішення (read-only, Claude-driven)
- Фіча з ринком → WebSearch, 3–5 конкурентів, таблиця Product·URL·Features·Value·Gap з датою і запитом.
- Внутрішня або pet-фіча → **не вигадувати ринок**: 2–3 «сусідні рішення, якими вже користуюсь або користувався» (застосунок, банк, таблиця) + рядок «як це робить легасі», якщо є. `N/A — internal` дозволений з причиною.

### 5. Стратегічні підходи (3 паралельні sub-agents)
Персони під мій ринок, кожен повертає Name / Thesis / For whom / Outcome metric / Key trade-off / Effort S-M-L:
- **Reuse** — перевикористати наявний модуль/легасі-потік, навіть якщо негарно.
- **Integrate** — узяти готове зовнішнє (постачальник, сервіс, файл-довідник).
- **Build minimal** — власна мінімальна реалізація рівно під проблему.

### 6. Multi-perspective review (3 паралельні sub-agents)
- **Engineer** — абстрактні ризики, без назв бібліотек/сховищ.
- **Support** — що прилетить у першу лінію: які тікети, як діагностувати, де користувач побачить, що щось не задано/не порахувалось. Для pet — «сам собі саппорт»: де Я дізнаюсь, що дані неповні.
- **User** — тертя, помітність, крива звикання.
Матриця 3×3 з обґрунтуванням у клітинках.

### 7. Trade-offs + edge cases (synthesis)
Pros/cons по підходах + 5–8 edge cases (дані, інтеграції, відмови, сезонні піки).

### 8. Devil's advocate (1 sub-agent, чиста сесія)
Без upstream-контексту: «5–10 attack vectors з production-сигналами». Найгостріший → §10 Risks.

### 9. RICE + правило малої бази (AskUserQuestion)
R ← §3 (для B2B — бронювання/сезон; для pet — мої випадки використання/рік), I ← §2+§8, C ← кількість TBD у §15, E ← сигнали §7.
**Правило малої бази: якщо Reach < 10 на квартал, фіча проходить тільки з Effort S.** Інакше — спершу різати scope (повторити Phase 7 для урізаного варіанта), не влазить у S — у парк. Confirm кожного числа через AskUserQuestion.

### 10. Feasibility (repo scan + AskUserQuestion)
Read-only скан репо на сусідні відвантажені фічі; Tech/Skills/Time ☑/☐ з цитатою «схоже на <фічу X>, вона зайняла <N>». Confirm через AskUserQuestion.

### 11. Recommendation (AskUserQuestion)
Вибір підходу + 3–5 речень, що цитують RICE (§11), Feasibility (§12), ≥1 клітинку §8, ≥1 gap §6. Confirm.

### 11.5. ExitPlanMode
План: mkdir, копія шаблона, застосувати glossary-терміни, заповнити секції, self-check, коміт. Якщо plan mode не активний — одразу Phase 12.

### 12. Execute
mkdir `docs/features/<slug>/`, копія `./templates/idea-brief.md`, дописати терміни у `CONTEXT.md` (формат «термін — речення. NOT-межа.»), заповнити всі секції + «Слід у словнику», frontmatter `status: Confirmed`, дати, RICE.

### 13. Self-check
- Всі секції шаблона заповнені (порожні H2 — видалити або `<!-- TBD -->`).
- Регекс заборонених термінів у тілі, з word boundaries: `\b(Postgres|PostgreSQL|Redis|Kafka|MySQL|Express|zod|pg|Symfony|Doctrine|TypeScript|JSONB)\b` + `p99`. Це продуктовий бриф — технології живуть у SPEC/ADR.
- ≤ 5 сторінок (~2200 слів).
- §13 цитує §6 + §8 + §11 + §12.
- «Слід у словнику» збігається з реальною дельтою CONTEXT.md за прогін.

### 14. Commit + next owner
Запропонувати (не виконувати): `01: idea for <slug> via discovery`. Наступний крок — PRD.

## Definition of Done

Як у оригіналі (бриф створений, секції заповнені, RICE/Feasibility confirmed, рекомендація з цитатами, checkpoint-и реально стріляли) плюс: правило малої бази застосоване й задокументоване у §11; «Слід у словнику» відповідає дельті CONTEXT.md.

## Anti-patterns (успадковані + свої)

- Вигадані конкуренти для внутрішньої фічі — краще чесні «сусідні рішення» або N/A.
- RICE, що ігнорує правило малої бази: «Reach 3, Effort L, але дуже хочеться».
- Devil's advocate у тій самій сесії — тільки чистий контекст.
- Технології у тілі брифа; рішення «яким сховищем» — не gate-1 питання.
- Пропуск питання про дедлайн сезону: фіча «встигнемо колись» у travel означає «через рік».
- Support-перспектива, переписана як друга Engineer-перспектива: Support говорить тікетами і симптомами, не архітектурою.
