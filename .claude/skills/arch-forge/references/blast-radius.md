# Радіус впливу — коли рішення варте окремого ADR (4 критерії)

Готовий скіл користується трьома критеріями: **≥ 3 днів переробки**, **≥ 2 модулі**, **чесна альтернатива**. У моїх репо найдорожче передумувати не код, а **схему даних**: кожне нове поле — SQL-файл у `migrations/`, кожна зміна типу — backfill, а PRD з prd-forge вже несе §9 Migration impact саме тому. Тож четвертий критерій — окремо, а не «всередині» незворотності.

## Критерії

| # | Питання | Спрацьовує, коли | Не спрацьовує, коли |
|---|---|---|---|
| 1 | **Незворотнє?** Переробка через 3 місяці ≥ 3 днів | зміна місця/форми зберігання; синхронна ↔ асинхронна взаємодія; стратегія ID; модель доступу | вибір бібліотеки в межах стека; значення конфігу; перейменування |
| 2 | **≥ 2 модулі?** Рішення бачать кілька BC або BC + presentation-контракт | новий порт між BC; зміна форми відповіді ендпойнта; value object у `shared/` | приватний метод репозиторію; внутрішня назва у одному use case |
| 3 | **Чесна альтернатива?** Через півроку хтось спитає «а чому не X?» і X — не страшмен | 2–3 серйозні опції, які два інженери обрали б по-різному | X виключений існуючим обмеженням (CLAUDE.md, ARCHITECTURE.md, SPEC.md) або очевидно гірший |
| 4 | **Зачіпає базу?** Породжує колонку / таблицю / CHECK / індекс / backfill у `migrations/` | нова колонка чи таблиця; зміна типу з backfill; нове обмеження, яке валідує старі рядки | обчислення поверх наявних даних; зміна лише DTO/відповіді; тимчасові структури в пам'яті |

## Правило

- **0–1 з 4** → inline у sad.md (рядок у §4/§5/§8 з одним речення «чому»).
- **2 з 4** → ADR.
- **«Зачіпає базу» + «чесна альтернатива»** → ADR завжди, навіть якщо переробка виглядає дешевою: дешева міграція сьогодні — це backfill на живих даних завтра.
- **Зворотний порт між BC** (новий напрямок залежності) → ADR незалежно від підрахунку — це рішення про форму всього репо, не фічі.
- Межа §4 нижча, як і в оригіналі: стратегічний стовп з 1 критерієм — кандидат на ADR, питаю явно «ADR чи inline?».

## Приклади з мого стека

- **Budget як колонки на `trips`** (trip-budget): незворотнє (перенос = міграція з backfill) ✓, 2 модулі (`trips` пише, `expenses` читає) ✓, альтернатива (окрема таблиця, окремий BC) ✓, зачіпає базу ✓ → 4/4, ADR.
- **`Balance` зі знаком у `shared/`**: 2 модулі ✓, альтернатива (послабити `Money`, голий number) ✓, базу не зачіпає, переробка — години → 2/4, ADR (бо бачать обидва BC).
- **Окремий `TripBudgetPort` замість розширення `TripStatusPort`**: альтернатива ✓, решта — ні → 1/4, inline (аргумент живе як відкинута опція у ADR про порт).
- **API-key middleware** (межа доступу): альтернатива «без ключа» вже виключена SPEC.md → 0–1/4, inline у §8.
- **Курс на витраті як `rate_micro BIGINT`** (multi-currency-summary): зачіпає базу ✓ + альтернатива (`NUMERIC`, float) ✓ → ADR завжди за правилом «база + альтернатива».

## Здоровий діапазон

XS/S — 2–4 ADR; M — 5–12; L/XL — 10–15. Понад діапазон — перевіряю, чи не зробив ADR з конфіг-значення; менше — чи не пропустив міграцію або зворотний порт.

## Закривальний самоогляд

1. §9 = дзеркало `adr/` (без сиріт в обидва боки), у кожному рядку — BC.
2. У кожному ADR є Status Accepted, ≥ 2 чесні опції, Links на PRD + §N SAD + сусідній ADR.
3. Прогнав би я ці 4 критерії ще раз — кожен ADR пройшов би знову?
4. Серед inline-рішень немає такого, що породжує міграцію.
