# PRD — multi-currency-summary

> **Inputs (required):** [idea-brief](./idea-brief.md) · [CONTEXT](../../../CONTEXT.md)
> **Reference module:** `src/expenses` — патерни: агрегат `GetTripSummary` (converted total — ще одна чиста функція над ним), typed domain errors, межова валідація вводу, `Money` у minor units.
> **Channels used:** Reference module + docs/features/trip-budget/PRD.md (сусідній PRD — межа між counted/uncounted успадковується звідти).

## 1. Context

У типовій закордонній поїздці 2–3 валюти, і підсумок по валютах окремо не відповідає на головне питання «скільки я реально витратив»; залишок з trip-budget порівнюється лише з витратами в base currency — у серпневій поїздці поза порівнянням лишилось ~40% суми. Сегмент чесний: «я і я», 4–6 поїздок на рік, закордонні — практично всі мультивалютні.

Чому зараз: перший прогін trip-budget показав, що лічильник неврахованих витрат — милиця, а не рішення; дедлайн сезону — поїздка в жовтні 2026, інакше бойова перевірка відкладається до зими.

Прийнятий вектор (idea-brief §13, Approach C): необов'язковий rate snapshot прямо на витраті, зафіксований один раз до base currency; підсумок показує converted total поруч із сирими сумами по валютах плюс чесний лічильник витрат без курсу. Жодних зовнішніх джерел курсів — інваріант словника.

Reference-патерни (traceability для стадій API/data model): перерахунок — чиста функція над наявним агрегатом підсумку, курс живе атрибутом витрати (не журналом), сирі суми й converted total рахуються з одного джерела. Decision override з фази критика: критик пропонував заборонити редагування курсу у finished поїздці за аналогією з витратами — overridden by author, rationale: пачкове дозаповнення курсів постфактум — заявлений у брифі сценарій (§10 mitigation), заборона його вбила б; заборона finished стосується нових витрат, не атрибутів наявних.

## 2. Goals

- Owner бачить у підсумку відповідь на «скільки я реально витратив» однією сумою в base currency, поруч із сирими сумами по валютах, а не замість них (§13).
- Курс на витраті видимий і виправний — на відміну від «магічних» авто-курсів TravelSpend (§13, gap з §6 брифа).
- Залишок бюджету перестає брехати на мультивалютних поїздках: витрата з курсом входить у порівняння з budget (§13, лікує головний ризик trip-budget).

## 3. Non-goals

- Автоматичні курси із зовнішніх джерел — інваріант словника «жодних зовнішніх залежностей за курсами» (idea-brief §5).
- Історичні довідники курсів і перерахунок «станом на сьогодні» — курс фіксується один раз на дату витрати (idea-brief §5).
- Мультивалютний бюджет — budget лишається однією сумою в base currency (idea-brief §5).
- Окремий журнал змін курсу — курс є атрибутом витрати; виправлення просто замінює значення (наслідок Edit US-04 у Socratic loop: «історія курсів» явно винесена за межі).

## 4. User stories

### US-01: Зафіксувати курс на витраті

**As an** owner
**I want** необов'язково вказати rate snapshot при введенні витрати в чужій валюті
**So that** витрата одразу входить у converted total без подальшої ручної роботи

### US-02: Побачити чесний загальний підсумок

**As an** owner
**I want** бачити converted total поруч із сирими сумами по кожній валюті
**So that** «скільки разом» видно одним числом, а сирі суми лишаються для звірки з чеками

### US-03: Бачити масштаб дірки

**As an** owner
**I want** бачити лічильник витрат без курсу поруч із converted total
**So that** я розумію, наскільки total неповний, і що саме дозаповнити

### US-04: Виправити курс заднім числом

**As an** owner
**I want** замінити курс на вже збереженій витраті
**So that** переплутаний напрямок курсу чи забуте поле — буденна правка, а не «тікет»

### US-05: Не вводити очевидне

**As an** owner
**I want** щоб для витрат у base currency курс 1 підставлявся сам і поле не питалось
**So that** зайвого тертя на кожній домашній витраті немає

### US-06: Дозаповнити курси постфактум

**As an** owner
**I want** пачкою доставити курси на витрати минулих днів, зокрема після завершення поїздки
**So that** «сила звички» перших днів не лишає total брехливим назавжди

## 5. Acceptance criteria

### AC-01 (US-01) — happy path

**Given** owner вводить витрату у валюті, відмінній від base currency поїздки
**When** owner вказує додатний rate snapshot
**Then** система зберігає курс атрибутом витрати, і converted total підсумку включає цю витрату перерахованою

### AC-02 (US-01) — validation

**Given** owner вводить витрату в чужій валюті
**When** вказаний курс нульовий або від'ємний
**Then** система блокує збереження і пояснює, що курс має бути додатним числом

### AC-03 (US-02) — happy path

**Given** у поїздці є витрати у кількох валютах, частина з курсами
**When** owner відкриває підсумок
**Then** підсумок показує сирі суми по кожній валюті ТА converted total у base currency, порахований лише з витрат, що мають rate snapshot

### AC-03b (US-02) — дрібна валюта (edge, доданий через Add edge case)

**Given** витрата у валюті з курсом у тисячі одиниць за одиницю base currency
**When** owner відкриває підсумок
**Then** перерахована сума відображається без округлення в нуль — точність minor units зберігається

### AC-04 (US-03) — happy path

**Given** у поїздці є витрати без rate snapshot
**When** owner відкриває підсумок
**Then** поруч із converted total видно лічильник витрат поза перерахунком — система не вдає, що total повний

### AC-05 (US-04) — виправлення курсу

**Given** витрата має збережений rate snapshot
**When** owner замінює курс новим значенням
**Then** converted total перераховується від нового курсу; попереднє значення ніде не зберігається і не показується

### AC-06 (US-05) — авто-курс для base currency

**Given** owner вводить витрату у base currency поїздки
**When** витрата зберігається
**Then** система сама фіксує курс 1 і не питає поле курсу — витрата одразу counted

### AC-07 — domain invariant: незмінна base currency

**Given** у поїздці існує хоча б одна витрата з rate snapshot
**When** owner намагається змінити base currency поїздки
**Then** система блокує зміну і пояснює правило: зафіксовані курси втратили б сенс — спершу поїздка без курсів, потім зміна валюти

### AC-08 (US-06) — lifecycle: finished не блокує дозаповнення

**Given** поїздка у статусі finished і в ній є витрати без курсу
**When** owner доставляє rate snapshot на такі витрати
**Then** система приймає курс — заборона finished стосується додавання нових витрат, не атрибутів наявних

### AC-09 (US-02) — cross-context: залишок бюджету лікується

**Given** поїздка має budget, і чужовалютна витрата отримала rate snapshot
**When** owner відкриває підсумок
**Then** ця витрата входить у порівняння з budget, remaining рахує її перерахованою, а лічильник неврахованих зменшується — converted total і залишок живляться з одного джерела

## 6. Non-functional requirements

| Aspect | Target | Measurement |
|---|---|---|
| Latency p95 підсумку з converted total | ≤ 250 ms | метрика `GET /trips/:id/summary` |
| Latency p95 збереження/правки курсу | ≤ 150 ms | метрика write-ендпойнта витрати |
| Throughput | ≥ 30 req/s на 1 інстанс | k6 smoke у CI |
| Availability | 99.0% | місячне вікно, наслідує SLO хостингу |
| Точність перерахунку | похибка ≤ 1 minor unit на витрату | minor units + фіксоване правило округлення, property-тест |

## 6.1 Security / privacy

- **Data classification:** internal — особисті фінансові записи owner-а.
- **Personal data touched:** нове поле — курс на витраті (число); PII немає.
- **Межа доступу:** як у trip-budget — лише owner; механізм успадковується з рішення по trip-budget (§8 там), нових меж фіча не додає.
- **Abuse cases:** сторонній читач підсумку — відмова без розкриття існування поїздки (успадковано); injection через поле курсу — курс лише додатне число, текст не приймається; spam-правки курсу — ліміт 60 запитів/хв як межа ручного користування.
- **Security review:** N/A — S-фіча, single-user, одне числове поле без PII, нових authz-меж немає.

## 7. Metrics / KPIs

- **Частка суми поїздки, врахованої у converted total** — baseline: 60% (серпнева поїздка), target: ≥ 95% за наступні 2 мультивалютні поїздки.
- **Частка чужовалютних витрат з курсом, введеним у день витрати** — baseline: TBD, план виміру: перша поїздка з фічею, порівняння дати витрати з датою появи курсу; target: ≥ 80% (перевірка ризику «сила звички» з §10 брифа).
- **Виправлення напрямку курсу** — baseline: 0 (поля не існувало), target: кожен «космічний total» діагностується правкою курсу без сторонньої допомоги; сигнал — кількість замін курсу на останніх витратах.
- **Latency p95 підсумку** — baseline: поточна метрика summary, target: ≤ 250 ms з перерахунком (повтор NFR як post-release KPI).

## 9. Migration impact

Нове поле `expense.rate` (додатне число, nullable — відсутність означає uncounted) — один SQL-файл у `migrations/`. Нових сутностей немає; converted total — обчислення поверх наявних даних, стану не додає. Для витрат у base currency курс 1 проставляється при збереженні, backfill наявних даних: усі старі витрати в base currency отримують курс 1 тим самим migration-файлом.
