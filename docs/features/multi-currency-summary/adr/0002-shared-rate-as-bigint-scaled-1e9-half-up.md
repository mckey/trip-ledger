# 0002 — Представляти курс value object-ом `Rate`: `BigInt` зі шкалою 10⁹ і округленням half-up; вхід — до 6 знаків після коми

- **Status:** Accepted
- **Date:** 2026-09-02
- **Deciders:** Vladimir Makarov (owner фічі, архітектор) — Socratic walk `arch-forge`

## Контекст

PRD §6 NFR: похибка перерахунку ≤ 1 minor unit на витрату; AC-03b: витрата у «дрібній» валюті не має округлюватись у нуль. PRD §8 залишив два питання: скільки знаків після коми приймати (4 чи 6, дефолт 6) і яке правило округлення (half-up чи банківське, дефолт half-up). Гроші у репо — цілі minor units (`Money`), а SAD trip-budget §8 зафіксував конвенцію «плаваюча точка заборонена» на всьому ланцюжку — тому арифметика на `number` з `Math.round` виключена конвенцією, а не розглядається як альтернатива.

## Радіус впливу (4 критерії)

| Незворотнє (≥ 3 днів) | ≥ 2 модулі | Чесна альтернатива | Зачіпає базу |
|---|---|---|---|
| ✓ — зміна шкали пізніше = backfill усіх `rate_nano` | ✓ — `shared` → `expenses` (BudgetBlock, репозиторій) → presentation (серіалізація) | ✓ — `NUMERIC` у БД + decimal-бібліотека | ✓ — тип колонки з міграції 0004 |

4 з 4 → ADR; «зачіпає базу» + «чесна альтернатива» — ADR за правилом і без підрахунку.

## Драйвери рішення

- PRD §6 NFR «Точність перерахунку: похибка ≤ 1 minor unit на витрату; minor units + фіксоване правило округлення, property-тест».
- PRD §5 AC-03b (дрібна валюта без округлення в нуль), §8 OQ #1 (грануляція вводу — дефолт 6), OQ #3 (округлення — дефолт half-up).
- trip-budget sad.md §8 Money & precision: «плаваюча точка заборонена»; CLAUDE.md: `shared/` — value objects без бізнес-логіки контекстів.
- sad.md §1 QG-1 і §10: одна точка округлення на converted total і на remaining.

## Розглянуті варіанти

1. **`Rate` у `shared/`: `BigInt`, шкала 10⁹.** `Rate.parse('0.9123')` приймає рядок з ≤ 6 знаками після коми і зберігає `912300000n`; `apply(money)` = `(amount × rate + 500 000 000) / 10⁹` цілочислово — half-up для додатних; `Rate.ONE` для base currency. У БД `BIGINT`, у мапінгу — рядок ↔ `BigInt`. Жодних нових залежностей.
2. **`NUMERIC(18,9)` у БД + decimal-бібліотека у коді** (`big.js`/`decimal.js`): точна десяткова арифметика «з коробки», але нова runtime-залежність у репо, де їх свідомо три (`express`, `pg`, `zod`), і два способи рахувати гроші поруч (`Money` цілими, курс — decimal).
3. **Шкала 10⁶ (`INTEGER`), рівно як дефолт PRD OQ #1.** Простіше пояснити («6 знаків і в базі, і на вході»), але для курсів на кшталт VND→EUR (≈ 0.000037 → `37`) відносна похибка ~3 %, яка на сумі 10⁸ minor units дає ~3.7 minor units — пробиває NFR.

## Результат рішення

**Обрано:** Варіант 1 — `Rate` як `BigInt` ×10⁹, half-up, вхід ≤ 6 знаків.

**Чому переміг:** тримає NFR із запасом на реальних «дрібних» валютах без нової залежності й без другого способу рахувати гроші; property-тест на випадкових цілих детермінований. Вхідна грануляція 6 знаків — питання зручності owner-а (закриває OQ #1), шкала зберігання 10⁹ — питання точності; розділення дозволило прийняти дефолт PRD на вході й не платити ним за точність. Half-up збігається з тим, як owner округлює на папері (OQ #3, дефолт PRD), і фіксується тут, бо це рішення про `shared/`, а не про колонку.

## Наслідки

**Позитивні:**
- Жодної нової залежності; арифметика в одному місці (`Rate.apply`), property-тестована (QG-1).
- Одне правило округлення для converted total і для remaining — числа у підсумку сходяться між собою.
- Курси реальних валют представлені без втрати: 10⁻⁹ — далеко за межами будь-якого курсу.

**Негативні:**
- `BIGINT` приходить з `pg` рядком → у репозиторії явний мапінг `String ↔ BigInt`; у JSON курс їздить десятковим рядком (`"0.912300"`), не числом — контракт фіксується на стадії API.
- Ще один value object у `shared/` (третій після `Money`, `Balance`) — треба пам'ятати, що `Rate` лише для коефіцієнтів.

**Нейтральні:**
- Перехід на банківське округлення, якщо колись знадобиться, — одна функція + оновлений property-тест, без міграції.
- Курси < 10⁻⁹ непредставні (`CHECK (rate_nano > 0)`) — зафіксовано як accepted debt у sad.md §11.
